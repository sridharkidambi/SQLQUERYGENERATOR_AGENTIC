# Evaluating the NL→SQL Pipeline

This validates the agentic system in `agent_orchestrator.py` against a
hand-written gold set (`eval_dataset.jsonl`) — the "manual query" side —
and checks it against what the system generates systematically. It is
meant to be re-run after any change to the retriever, the generation
prompt, the schema, or the router.

## The gold set

`eval_dataset.jsonl` is 18 cases, each with:

- `nl_query` — what a real user might type.
- `gold_sql` — a SQL statement I wrote and hand-verified against
  `schema.sql`, not generated by the system under test. This is the
  "manual query" ground truth.
- `gold_tables` — which tables a correct retrieval should surface, used
  to score the retriever independently of the generator.
- `scope` — `SQL_INTENT` or `OUT_OF_SCOPE`, to score the router.

Coverage is deliberately spread across: simple lookups, joins,
aggregations, a correlated subquery, a window function, enum/derivative
filtering, and four out-of-scope cases (a mutation attempt, chit-chat, an
unrelated domain question, and a prompt-injection attempt asking the
system to ignore its instructions and dump PII). That last group matters
as much as the SQL-correctness cases — a system that never refuses
anything isn't validated, it's just generating.

**This set is a starting point, not a finished benchmark.** Before relying
on it, add cases that reflect your actual users' phrasing and your
highest-risk queries (large aggregations, anything touching PAN numbers
or account balances, ambiguous asks that could resolve to more than one
correct table).

## Two layers of metrics, and why both

### A. Deterministic (`run_deterministic`, always runs, no LLM judge)

| Metric | What it catches |
|---|---|
| Intent accuracy | Router correctly separating in-scope data asks from everything else, including the injection case |
| SQL valid rate | Generated statement parses, is read-only, and every table/column it references actually exists (via `ValidationAgent`) |
| Table retrieval precision/recall | Retriever pulled the right tables — and didn't pull irrelevant ones — before generation even happens |

These are cheap, deterministic, and safe to run on every commit. They
catch outright breakage (bad joins, hallucinated columns, the router
letting a mutation request through).

### B. LLM-judged (`run_deepeval_metrics`, DeepEval)

Exact-string SQL comparison is a bad metric here: two semantically
identical queries can differ in join order, alias names, or CTE-vs-subquery
structure. So the generation-correctness check is delegated to an LLM
judge via DeepEval's `GEval`:

- **`sql_correctness`** — given the NL request, the gold SQL, and the
  generated SQL, does the judge believe they'd return the same result?
  Scored 0–1, threshold 0.6.
- **`ContextualPrecisionMetric` / `ContextualRecallMetric`** — DeepEval's
  built-in RAG metrics, scoring whether the retrieved table/column chunks
  were the relevant ones and ranked sensibly, using the gold SQL as the
  reference for "what should have been retrieved."

**Why DeepEval over RAGAS here:** both frameworks offer this same metric
class (custom LLM-judged correctness + contextual precision/recall). In
building this harness, pulling `ragas` into this project's environment
broke on a `langchain_community` → `langchain_core` version conflict with
the `langchain`/`langgraph` stack already pinned for the agents (a known
sharp edge — ragas pulls in a fairly deep, version-sensitive langchain
dependency tree). DeepEval's dependency footprint is lighter and decoupled
from the orchestrator's own LLM client, so it was the more stable choice
for this repo as-is. If you'd rather standardize on RAGAS project-wide —
e.g. because you're already using it elsewhere — install it in its own
virtualenv (isolated from `agent_orchestrator.py`'s dependencies) and use
`run_ragas_retrieval()` in `evaluate.py` as a drop-in replacement for the
contextual precision/recall half; the deterministic and `GEval` checks are
framework-independent either way.

### Which judge model DeepEval calls

By default DeepEval's metrics call OpenAI (`OPENAI_API_KEY`). To judge
with Claude instead, wrap the Anthropic client as a `DeepEvalBaseLLM` and
pass it as the `model=` argument to `GEval` / `ContextualPrecisionMetric` /
`ContextualRecallMetric` in `evaluate.py` — DeepEval's docs cover the
`DeepEvalBaseLLM` interface (`generate`, `a_generate`, `get_model_name`).
Do this before relying on judged scores in CI if you don't want an OpenAI
dependency at all.

## Running it

```bash
pip install deepeval sqlglot psycopg2-binary anthropic
export OPENAI_API_KEY=...       # DeepEval's default judge, unless you wire in Claude
export ANTHROPIC_API_KEY=...    # generation agent under test

python evaluate.py --dsn "$PGDSN" --dataset eval_dataset.jsonl
```

Fast, judge-free loop while iterating on the retriever/router:
```bash
python evaluate.py --dsn "$PGDSN" --skip-llm-judge
```

Output: a printed per-case table, an aggregate summary, and a full
`eval_report.json` (per-case scores + reasons) for tracking over time —
diff `eval_report.json` between runs to see exactly which cases regressed.

## Reading the results

- **Intent accuracy < 1.0 on the out-of-scope cases specifically** is the
  most important thing to look at before anything else — a router that
  lets `q14`–`q17` through means unvalidated SQL generation on mutation
  attempts or injection attempts. Treat any regression here as a blocker,
  not a tuning nit.
- **Low table recall, high precision** on a case usually means the
  retriever's `top_k` is too small or the embedding model isn't
  surfacing a less-obviously-worded table (e.g. "breached their limit"
  → `risk_limits.is_breached`); check the chunk text for that table in
  `schema_embeddings` first.
- **`sql_valid = True` but low `geval_correctness`** means the query runs
  and references real columns but doesn't actually answer the question —
  usually a missing filter or wrong aggregation grain. This is exactly the
  class of error the deterministic checks can't catch, which is the point
  of running both layers.
- Track `avg_geval_sql_correctness` and `sql_valid_rate` over time as the
  two headline numbers; the others are diagnostic for *why* those moved.

## What execution-accuracy would add (not included here)

The strongest possible check — actually running both the gold and
generated SQL against a representative seeded database and comparing
result sets row-for-row — is intentionally not implemented in
`evaluate.py`. It needs realistic seed data (volumes large enough for the
query planner's choices and aggregate results to be meaningful), which is
deployment-specific. If you build a seed fixture, add an
`execution_match` deterministic check next to `sql_valid` in
`run_deterministic()`: run both statements read-only, `set`-compare the
result rows, and treat a mismatch as a hard failure regardless of what the
LLM judge says.
